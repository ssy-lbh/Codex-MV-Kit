# 贡献与 GitHub 发布准备

贡献应让另一位用户能够在自己的歌曲、角色和机器上重复操作。优先提交通用算法、校验、合成测试与解释清楚的模板；不要把个人作品素材混入工具仓库。

## 本地开发

阅读根目录 [AGENTS.md](../AGENTS.md)，安装步骤见 [README](../README.md)。Python 包名为 `codex_mv`；FFmpeg/FFprobe 是外部工具，路径可配置。对依赖、时间模型或 JSON schema 的变更同时更新实现、测试和示例。

修改时间、音频、项目或渲染逻辑后执行：

```text
python -m unittest discover -s tests -v
python -m codex_mv --help
```

FFmpeg 可用时还要运行 README 中的合成端到端 demo，包含校验、短片渲染与归档恢复。测试应覆盖真实边界，例如裁剪相位、最后一帧、完整音频窗口或路径越界；不要只验证实现抄写出来的同一表达式。纯文字改动检查本地链接、参数和隐私即可。

使用有界缓存，不用整视频 preload 换取单次小样成功；FFmpeg 调用采用参数列表。不要引入默默上传素材、申请密钥或产生云端费用的默认路径。普通本地编辑和检查可直接完成。

## Issue 与 PR

提供最小 synthetic reproduction：版本、输入项目、期望行为、实际行为、错误文本，以及适用时的帧数或样本计数。避免附真实歌曲、歌词、未授权帧和个人日志。错误里含绝对路径时先替换为通用相对路径。

PR 描述先说明具体触发条件及行为变化，再写相关验证。时间相关修复给出 global start、fps 和边界；视觉修复应包含允许公开的合成前后对比，并明确人工审片是否完成。

代码 MIT 许可与外部素材授权分开处理。新增字体、音乐、插画或模型输出时，记录来源和再分发许可；无法确认就不要把文件加入公共仓库。生成内容也需要参考来源和适用条款记录，不能自动标记 CC0。

## 发布前本地检查

先完成所有可逆本地准备，再申请尚未获得的发布授权。准备工作包括：

1. 核对测试和合成 demo，检查文档命令确实对应当前 CLI。
2. 检查 Git 实际跟踪清单和 staged diff；`.gitignore` 不会排除已经跟踪的文件。
3. 搜索私人姓名、邮箱、机器绝对路径、源项目名称、密钥、字幕文本和日志引用。仅有关键词扫描不足以证明无隐私，需人工查看变更。
4. 审查媒体、字体、压缩包、测试 fixtures 和 Git 历史。公共 demo 使用合成输入；构建产物和用户媒体留在忽略目录。
5. 确认 README、LICENSE、来源说明、依赖和可执行示例齐全；给出将发布的远程仓库、可见性和文件范围。

可使用这些只读命令审查：

```text
git status --short
git ls-files
git diff --stat
git diff --cached
```

不要把真实路径、用户名或凭据放进公开命令示例；私有扫描结果保持私有。若仓库尚未初始化，先把上述审查作用于当前文件清单，Git 操作在授权范围内再执行。

## GitHub 发布

用户明确要求创建/发布 GitHub 仓库时，该授权可覆盖任务描述中的对应操作；否则本地准备完成后，展示仓库名、可见性、文件范围和检查结果，取得明确发布授权，再执行创建 remote、push、release 或上传附件。不要因写了 README 就擅自公开。

发布应使用用户选定账号和实际可用的 GitHub 工具。不要自行读取或外传令牌，不要声称每个 Codex 环境都已连接 GitHub。无需改写全局 Git 配置来适配仓库；缺少账号或 remote 信息时只提出当前真正阻塞的一项。

对已公开仓库，删除大文件、重写历史、force-push、改可见性和移除 release 是不同风险的操作，需要任务范围内明确授权。先准备可审查的修复，不用历史重写来掩盖未经检查的媒体泄漏。

## 给 Codex 的仓库说明

根 `AGENTS.md` 放本仓库稳定约定，局部差异使用适合宿主的目录指引。不要改用户全局配置或声称其他代理必然按同一规则加载。[Codex 官方 AGENTS.md 文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md)说明当前目录层级发现机制；实际会话应核对加载结果。
